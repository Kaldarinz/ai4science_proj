# ДЗ 2. Проверка численных извлечения данных из базы данных и устойчивости их классификации

Курс ШАД «ИИ-ассистенты для исследователя. AI4Science», осень 2026. Автор проекта: Антон Попов.

**Основной отчёт:** [`results/verifier/REPORT.md`](results/verifier/REPORT.md).
В нём собраны постановка задачи, методика, дерево подцелей, журнал попыток,
результаты, ограничения и таблица авторства. Этот README — точка входа:
что проверяется, где лежат материалы ДЗ 2 и как повторить проверку.

## 1. Что проверяется

Общая цель проекта — сравнить текстовые утверждения статей о зависимости
размера золотых наночастиц от флюенса или энергии лазерных импульсов
с численными данными этих же статей.

**ДЗ 2 проверяет отдельный компонент:**

1. Из снимка моей базы данных научных статей (`ablation_db`) выбираются оцифрованные измерения
   и строятся ряды «размер — флюенс» или «размер — энергия импульса»
   с одинаковыми остальными условиями эксперимента.
2. Размеры и их ошибки рассчитываются по зафиксированным правилам.
   Каждому ряду присваивается форма с учётом ошибок: `flat`, `increasing`,
   `decreasing`, `peak`, `valley` или `irregular`.
3. Независимый проверяющий код проверяет договор о данных и рядах.
   Тесты на свойствах проверяют поведение вычислительных функций.
4. Численный эксперимент оценивает чувствительность формы ряда
   к возмущениям размеров при заданной модели шума.

## 2. Быстрый запуск на чистой копии

Проверенное окружение — Python 3.12.3; зависимости указаны
в [`requirements.txt`](requirements.txt).

```sh
set -e

git clone --branch hw2 https://github.com/Kaldarinz/ai4science_proj.git hw2-check
cd hw2-check
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt

# Одна команда, выносящая вердикт верификатора ДЗ 2:
.venv/bin/python -m pytest checks/verifier -q
```

Ожидается **82 passed**, код возврата **0**. Та же команда записана
в [`AGENTS.md`, §1](AGENTS.md#1-readiness-criterion).
После установки зависимостей ни сеть, ни PDF статей, ни сервер БД
для этой проверки не нужны.

Это **не** `checks/check.py`: тот проверяет извлечение цитат, требует PDF
и проверяет коммиты результатов. Для воспроизведения ДЗ 2 запускается
именно команда выше.

## 5. Как повторить численный эксперимент

**Выполнять в отдельном клоне из §2, не поверх архивных результатов
в рабочем репозитории:** команды перезаписывают файлы этапов
в `results/verifier/`. При любой ошибке остановиться.

```sh
set -e

cp results/verifier/summary.csv results/verifier/summary.expected.csv
.venv/bin/python checks/verifier/run.py dry
.venv/bin/python -m pytest checks/verifier -q
.venv/bin/python checks/verifier/run.py smoke
.venv/bin/python checks/verifier/run.py full
cmp results/verifier/summary.expected.csv results/verifier/summary.csv
```

| Этап | Что происходит |
|---|---|
| `dry` | Проверка снимка и публичных рядов для обеих моделей; ожидается 0 нарушений |
| Короткая проверка | Все свойства, эталон и тесты проверяющего кода; ожидается 82 passed |
| `smoke` | Все ряды и обе модели, seed 0, 100 реализаций шума; 20 строк |
| `full` | Все ряды и обе модели, seeds 0–4, по 1000 реализаций шума; 100 строк и итоговая сводка |

Каждый `smoke` и `full` повторяет проверку договора и тесты верификатора.
`full` требует полного успешного `smoke` для того же снимка и тех же
исходников. Поэтому после изменения исходников или `METHOD.md` нужно
заново выполнить `smoke`, а не использовать старый манифест.

Baseline — ряд с теми же x и ошибками, но постоянным размером:
средним исходных размеров с весами, обратными квадратам ошибок `primary`.
Шум нормальный, с исходными ошибками `primary`; одни и те же возмущения
подаются на обе модели и на baseline. Ошибки не пересчитываются,
отрицательные реализации не отсекаются. Устойчивость — доля сохранений
исходной формы; Δ — разность этой доли и доли той же формы у baseline.
Интервалы и тесты считаются по пяти оценкам для отдельных seed,
а не по 5000 якобы независимым экспериментальным измерениям.

Поддержка формы требует одновременно `p_holm < 0.05` и `Δ ≥ 0.20`;
устойчивость — нижней границы 95%-го интервала не менее `0.80`.
Успешное выполнение кода не означает, что каждый ряд обязан пройти
эти научные критерии. Их невыполнение — допустимый результат эксперимента.

## 6. Как воспроизвести пойманную ошибку

Ошибка **внесена намеренно в отдельную ветку `bug/point-order`**:
в `classify_shape` сортировка точек заменена сохранением входного порядка.
Коммит ошибки — `cf188ed7f3618b3334af263eb67a7ad54783b5e0`;
правильный родитель — `776a2fe`. В `main` дефекта не было,
ветку ошибки нельзя сливать в `main`.

Из корня полного клона с установленным venv; путь `../hw2-bug`
должен быть свободен, а коммит ошибки — доступен в клоне:

```sh
set -e

PYTHON="$PWD/.venv/bin/python"
git worktree add --detach ../hw2-bug cf188ed7f3618b3334af263eb67a7ad54783b5e0
status=0
(cd ../hw2-bug && "$PYTHON" -m pytest checks/verifier -q) || status=$?
test "$status" -eq 1
```

Ожидается **1 failed, 81 passed**: падает именно
`test_point_order_does_not_matter`, а не импорт или настройка окружения.
Hypothesis сокращает пример до двух точек: их перестановка превращает
`increasing` в `decreasing` в ошибочной функции. На правильной реализации
обе перестановки дают `increasing`. Проверяющий код при внесении ошибки
не менялся. Это демонстрация нарушения договора чистой функции,
а не утверждение, что ошибка изменила форму реального ряда из снимка.
Полная история «до/после» — в отчёте, §6, и `caught_error.md`.
